# 适配度评估:这个仓库适合"从零写"吗

阶段 0 跑通后、画地图前,回答五问给仓库定档。答案写进 `00-scope.md` 的"适配度评估"一节(模板 `templates/scope.md`)。

## 五问

| # | 问题 | 判定 |
|---|---|---|
| 1 | 有没有说得清的内核 | 一句话能说清"把 __ 变成 __ 的核心机制"→ 有;要绕几个条件才说得清 → 无 |
| 2 | 本地能否确定性运行 | 不用 GPU/大权重/网络服务也能跑最小输入,同种子输出稳定 → 能 |
| 3 | 有没有参照实现可对账 | 原仓库可安装、能保存输出当 oracle,或有公开报告数字可核对 → 有 |
| 4 | 内核能否压到约 5–15 个组件、一两千行内 | 组件越少越适合 |
| 5 | "从零"的边界在哪 | 列出:允许直接用哪些底层库(标准库、渲染器),必须自己写哪些(内核路径上的零件) |

## 三档

| 档位 | 条件 | 做法 |
|---|---|---|
| **A 完整从零** | 五问基本满足 | 完整流程,输出与原仓库同输入下对账(逐字/`allclose`/hash) |
| **B 内核从零 + 其余导读** | 内核清晰,但仓库大或工程味重 | 只重建内核(骨架逐渐替换 Dummy),其余部分(config/CLI/分布式/数据准备)带注释导读 |
| **C baby 版** | 内核不清 / 不能确定性运行 / 没有 oracle | 抽核心思想做 baby 项目,心智模型为主要交付物(见 `references/baby-mode.md`) |

## 流程

1. 阶段 0 之后即做,把五问答案、档位、理由、从零边界写进 `00-scope.md`。
2. 档位有争议时(五问一半指向 A 一半指向 C)**先问用户**,不自己硬选。
3. 选定后分流:A 走完整流程;B 只对"本质"组件做阶梯与对账;C 走 baby 模式。

## 与"诚实边界"的关系

选 B 或 C 时,每章"诚实边界"框必须写明:**哪些部分没有从零重建、为什么**。读者不能误以为书本重建了全部。
