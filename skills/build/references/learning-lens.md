# 四层透镜:从"看懂"到"融会贯通"

> sc 插件的学习 skill(`sc:blog`、`sc:repo`、`sc:dots`、`sc:build`)共用本文件,各份内容一致;改一份,同步其他几份(仓库根目录 `scripts/check_sync.py` 会检查)。

"看懂"是能跟着别人的讲解走完一遍;"融会贯通"是**拿掉讲解,自己能在四个层次之间上下走、并和已知的东西横向连上**。本文件给出这四层、两种走法和一组自测题,供各 skill 在提炼、讲解、收尾时使用。四层透镜回答"学到什么程度";按什么顺序学,见学习循环(插件根目录 `shared/learning-loop.md`:用 → 切 → 造 → 验 → 融 → 沉,以及收尾三问)。

## 一、四层

| 层 | 回答的问题 | 合格的样子 | 常见的假货 |
|---|---|---|---|
| **思想**(core idea) | 它押注了什么?要化解的根本矛盾是什么? | 剥掉项目名、框架名后一两句话说得清,且能说出"为了 A 放弃了 B" | 功能介绍("它是一个高性能的 X 库") |
| **心智模型**(mental model) | 它在脑子里应该是一个什么样的"可运转的模型"? | 能**预测**:给一个新输入/新情形,不跑代码也能说出会发生什么;知道它在哪里失效 | 比喻或口号("就像一个漏斗"),说不出哪里像、哪里不像 |
| **架构**(architecture) | 系统怎么切成零件?零件之间的边界、接口、数据流和控制流是什么?为什么这样切? | 能画出 3–7 个零件的图,每条边写出传的是什么(类型/shape);每个边界能说出一条"设计决策" | 目录树或模块清单("utils/ 放工具函数") |
| **实现**(implementation) | 关键的几行代码在哪里、守护什么不变量、处理了哪些边角? | 能指到 `path:line`,并说出"这一行删掉会坏什么" | 逐行翻译代码("这里定义了一个变量") |

四层的关系:**思想决定架构怎么切,架构决定实现在哪里难,实现的难处又反过来检验思想是否成立。** 只会其中一层,就是"知道很多但连不起来"。

## 二、两种走法

### 纵向贯通:上下打通

- **向下追**:从一条思想出发 → 它落在架构的哪条边界上 → 由哪几行代码实现(`path:line`)。追不到代码的思想,多半是作者的愿景,不是系统的事实。
- **向上收**:从一段关键代码出发 → 它在守护哪条不变量 → 服务于哪个设计决策 → 体现哪条思想。收不上去的代码,多半是工程细节(可以跳过)或你还没看懂的地方(要回头)。

产物是一张**贯通表**,每行一条线,四层各填一格,外加证据:

| 思想 | 心智模型 | 架构落点 | 实现落点 | 证据 |
|---|---|---|---|---|
| 用空间换重复计算 | 每一步只算"新来的那个",旧的从缓存取 | 生成循环与注意力之间多一个 KV 缓存组件,接口是 `(k, v)` 追加 | `model.py:212` 拼接缓存 | 运行输出 / commit / 原文 |

一条线缺格,就是一个学习缺口,如实写"未找到",不要编。

### 横向连接:和已知的东西连上

一个新想法只有挂到已有的知识上,才不会过两天就忘。连接只用四种关系(与 `sc:dots` 的定义一致):

- **同源异形**:表面不同,本质是同一个机制(要写得出共同机制、区别、对两边都成立的那句话);
- **张力**:两个想法互相拉扯,各自在什么场景占上风;
- **依赖**:A 成立是因为 B 先存在;
- **传承**:它继承自更早的某个东西。

没有真实关系就不连。**宁可漏连,不可错连。**

## 三、设计决策卡(架构层的最小单位)

每个值得学的设计决策写一张,一张五行:

| 项 | 内容 |
|---|---|
| 问题与约束 | 当时要解决什么、受什么限制(规模、延迟、团队、兼容) |
| 备选方案 | 至少一个"显而易见但没被选"的做法 |
| 选择与代价 | 选了什么;为此放弃了什么 |
| 证据 | `path:line` / commit / PR / Issue / 原文;找不到写 `[推断]` |
| 约束变了会怎样 | 规模 ×100、换成分布式、换成离线……哪个决策最先需要推翻 |

最后一行最有价值:它把"记住这个设计"变成"理解这个设计成立的条件"。

## 四、自测题(读者合上书能答出,才算贯通)

每次学习收尾时,从下面挑 3–5 题,每题都要有可检验的答案要点:

1. **复述**:不看材料,用自己的话讲一遍思想与心智模型。
2. **预测**:给一个新输入或改一个参数,先写下预期结果,再运行/对照核对。
3. **向上收**:随手指一行关键代码(或原文里的一个细节),说出它为什么存在。
4. **向下追**:给出一条思想,指出它落在哪个零件、哪几行。
5. **改约束**:约束变了(规模、硬件、需求),哪个零件最先要改?为什么?
6. **迁移**:在另一个领域里,这个思想以什么面目出现?
7. **反例**:什么情况下它不成立?

## 五、来源分散时:拼成一条路

研究一个新方向时,想法常常散在论文、代码仓库、权重配置和零散笔记里。融会贯通的前提,是先把它们拼成**一条从基本原理到能跑的代码的路径**,然后自己沿着它构建一遍——理解一个东西最好的办法,就是自己构建一个。

- **每个来源有角色**:讲原理、给规格、当裁判、补实现细节;非官方实现只当对照参考。
- **分歧是学习点**:同一件事各来源说法不一时,记下各自怎么说、以谁为准、为什么。"实际是怎么做的"以权重和官方代码为准,"本来想怎么做"以论文为准。
- **没写的东西要显式补**:所有来源都没交代的细节(初始化、归一化位置、eps、采样参数……),补了就写明取值和依据,不悄悄填上。
- **每一步都有裁判**:能对上权重就不只对论文数字,能对上论文数字就不只看玩具实验(见 `sc:build` 的 `references/oracles.md`)。

## 六、不要这样做

- 只讲一层:全是思想(空)或全是实现(碎)。
- 把架构写成目录清单;把心智模型写成比喻;把思想写成功能介绍。
- 为了填满贯通表而编造落点或证据。
- 把训练记忆当证据:作者"为什么这么做",没有原文或代码依据就标 `[推断]`。
