# 设计路径:从基本原理到能跑的代码

一条好路径,让学习者不用自己去论文、仓库和笔记之间来回拼:每一步都知道为什么要做、照着谁做、做完怎么确认做对了。

## 一、倒着设计,正着走

1. **先定终点**:终点演示要具体到能跑(输入什么、输出什么、用什么指标说明它成了)。
2. **倒推前置**:要让终点成立,上一步必须已经有什么?一路倒推,直到只剩"会基础 Python"。
3. **正着排成里程碑**:每个里程碑一个新概念,结束时有一段能跑、能验证的代码。3–10 个里程碑;超过 10 个就拆成两条路径(先学前半条)。

## 二、每个里程碑写什么

| 项 | 写什么 |
|---|---|
| 新概念 | 只有一个;一句话 |
| 为什么需要 | 上一个里程碑在哪里不够——能跑就跑给学习者看(先失败) |
| 来源 | 论文第几节/公式几、仓库 `path:line`、权重里对应的参数、笔记链接;多个来源说法不同时指向差异表 |
| 裁判 | 怎么确认做对了(见 `oracles.md`):对上 logits / 官方输出 / 论文数字 / 不变量 / 玩具实验趋势 |
| 四层 | 这一步主要在补哪一层:思想、心智模型、架构还是实现 |
| 算力 | CPU 上大约跑多久;要 GPU 的标出来,并给 CPU 上的缩小版 |

## 三、排序的几条经验

- **先用,后造**:先加载现成的东西把终点演示跑一遍(例如用开放权重生成文本),学习者先看见目标;再一层层换成自己写的。
- **先量,后改**:训练或优化类的里程碑之前,先有评估——没有尺子,就看不出改动有没有用。
- **先推理时,后训练时**:不改权重就能做的(采样、搜索、投票、自我修正)放在前面,便宜、可在 CPU 上做;改权重的(微调、强化学习、蒸馏)放在后面,并给出缩小版。
- **朴素版本先跑**:论文要打败的那个基线,先实现出来;新方法的价值要在同一预算下和它对比才看得见。
- **工程细节放最后或放附录**:分布式、显存优化、吞吐优化不进主线。

## 四、示例:主题"推理模型"

一条可能的路径(实际的来源、裁判、规模在 `sources.md` 里按用户手上的材料定):

| # | 里程碑 | 新概念 | 裁判 |
|---|---|---|---|
| 1 | 加载一个小的开放权重模型,让它逐个 token 生成回答 | 自回归生成 | 和参考实现贪心解码的输出逐 token 一致 |
| 2 | 搭评估:一组有标准答案的题,自动抽取并核对答案 | 可验证的评估 | 手工核对几道题的抽取结果;报告准确率与题数 |
| 3 | 推理时扩展:多采样几次,多数投票 | 用更多推理算力换准确率 | 同一题集上对比单次与投票,多个种子,看提升是否稳定 |
| 4 | 让模型检查并修改自己的答案 | 自我修正 | 同上;记下修对和改错的数量 |
| 5 | 用可验证的奖励做强化学习(缩小版) | 奖励、优势、策略更新 | 小规模上奖励曲线上升;评估准确率与第 2 步的基线对比 |
| 6 | 用强模型的推理过程做蒸馏(缩小版) | 用数据而不是奖励传递能力 | 与第 5 步在同一预算下对比 |

这条路径体现了上面的经验:先用现成权重(1),先量(2),推理时(3–4)在训练时(5–6)之前。每一步的裁判都能在学习者自己的机器上跑出来。

## 五、路径画完后检查

1. 只看里程碑标题,能不能说出这个主题的来龙去脉?
2. 每个里程碑结束时,是不是都有能跑的代码和一个裁判?
3. 有没有哪一步同时加了两个新概念?
4. 每一步的来源都写了吗?来源之间的分歧都进了差异表吗?
5. 最难的那一步有没有给 CPU 上的缩小版?
