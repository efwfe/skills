# 不同材料怎么拿全

`scratch:blog` 处理四类材料:博客文章、论文、演讲(视频)、设计文档(RFC / ADR / PEP / 设计说明)。重建的方法相同(解剖 → 心智模型 → 台阶 → 贯通),差别在**怎么把原文和图拿全**,以及解剖时侧重什么(见 `dissection.md` 的体裁一节)。

总规则不变:拿不全就停下来告诉用户,请他提供原文,**不要凭标题、摘要或记忆编造**。

| 类型 | 怎么认出来 | 学习记录前缀 |
|---|---|---|
| 博客 | 个人站、Medium、公司技术博客 | `blog-` |
| 论文 | arXiv、ACL/NeurIPS/USENIX 等、`.pdf`、有摘要和参考文献 | `paper-` |
| 演讲 | YouTube、B 站、会议录像、幻灯片链接 | `talk-` |
| 设计文档 | RFC、PEP、KEP、ADR、`docs/design/*.md`、"Design Doc" | `doc-` |

## 博客

见 SKILL.md "输入"一节:`curl` 拿原始 HTML 转文本,逐张下载并打开看图。

## 论文

1. **优先拿 HTML 版**:arXiv 论文先试 `https://arxiv.org/html/<id>`(新论文大多有),图和公式都在,按博客的办法处理。
2. **只有 PDF 时**:下载到工作目录,用 Read 工具按页读 PDF(能看到图表;超过 10 页时用 `pages` 分段,每次最多 20 页)。需要大段纯文本做检索时,再用 `pdftotext`(有的话)或 `uv run --with pypdf python -c "..."` 抽文本。
3. **图**:论文的主图(架构图、主实验表)通常承担一半论证。图清单照建;沿用原图时截图对应页或用 HTML 版的图片,图注写清"图 N 出自原文第 X 页"。
4. **附录与代码**:论文常把关键细节放附录;有官方代码仓库的,记下链接——想继续深挖时可以交给 `/scratch:repo` 或 `/scratch:dots`。

## 演讲 / 视频

1. **拿文字稿**,按顺序试:
   - 用户直接粘贴字幕或文字稿;
   - 本机装了 `yt-dlp` 时:`yt-dlp --skip-download --write-subs --write-auto-subs --sub-langs "zh-Hans,zh,en" --convert-subs srt <链接>`;
   - 都不行就停下来请用户提供文字稿。只有标题和简介时**不要开写**。
2. **幻灯片**:演讲者常公开 PDF 或 Speaker Deck,找到就当作"图"处理;没有时,"图"一栏如实写"只有口头描述"。
3. **引用位置**:用时间戳代替页码(`[12:34]`),核验时据此回查原话。
4. 自动字幕常把术语听错,遇到读不通的地方,对照幻灯片或上下文判断,判断不了的记进"边界"。

## 设计文档(RFC / ADR / PEP / 设计说明)

1. **拿原始文本**:GitHub 上的文档用 raw 链接(`raw.githubusercontent.com/...`),保留标题层级。
2. **记下状态**:草案 / 已接受 / 已被取代 / 已撤回,以及日期。已被取代的,找到取代它的那份并在"边界"里写明。
3. **现成的设计决策卡**:设计文档通常自带"背景 / 目标与非目标 / 考虑过的方案 / 决定 / 后果",直接对应设计决策卡五行(`learning-lens.md` §三)。重点放在**被否决的方案和理由**上,那是作者品味最清楚的地方。
4. **和实现对照**:文档描述的是"打算怎么做"。有对应代码时,看实现是否照做、哪里改了;改了的地方往往是最值得学的教训,但要有证据(commit、后续文档),没有证据就标 `[推断]`。
