# 练习模式:你来写,Claude 当教练

出书模式里,Claude 把仓库重建出来,写成给别人读的课程。练习模式里,**学习者就是用户本人,代码由用户亲手写**:谁亲手重建,谁才真的学会。Claude 负责备课(地图、梯级、测试、oracle)、出题、给提示、评审和追问,不代写实现。

## 一、和出书模式的区别

| | 出书模式 | 练习模式 |
|---|---|---|
| 谁写实现 | Claude | 用户 |
| 产物 | `chapters/`、`figures/`、讲义 | `lab/`:每个组件一个练习目录 + `PROGRESS.md` |
| "先失败" | 正文里跑给读者看 | 用户运行测试,亲眼看它红 |
| 对账 | 章末 `assert` | 测试:形状、不变量、与 oracle 对比 |
| 写作流水线、lint、配图 | 要 | 不要 |
| 四层贯通 | 写进"设计取舍"小节 | 用户先答贯通题,Claude 再补 |

阶段 0–2.5(定义、适配度、地图、追路径、架构与思想)照常做,但只为备课服务:`00-scope.md` 写短,够定梯级和测试即可。档位 C(baby)同样适用:练的是 baby 实现,对照表照做。

## 二、开始前问一次

只问一个问题(AskUserQuestion),答案写进 `lab/PROGRESS.md` 顶部:

- **步子**:小步(每级只改几行,提示给得早)/ 中步(默认)/ 大步(一级一个完整函数,提示给得晚)。

用户的 Python 水平、领域背景,能从对话或 dot 库里看出来的就不问。原仓库不是 Python 时,默认仍用 Python 重建内核(练的是机制,不是语言);用户想用原语言,就按原语言出骨架和测试。

## 三、备课:每个组件一个练习目录

```
lab/
  PROGRESS.md            # 进度与"我自己的话",模板 templates/lab-progress.md
  pyproject.toml         # uv 管理,只放 pytest 与必要的库
  oracle/                # 固定种子保存的原仓库输出(与出书模式同法)
  NN-<组件>/
    README.md            # 这一组件的题面,模板 templates/lab-readme.md
    impl.py              # 用户写的地方:签名 + docstring + raise NotImplementedError
    test_NN.py           # 每级一组测试,模板 templates/lab-test.py
  .answers/              # Claude 的参考实现,只用来验证测试;写进 .gitignore,告诉用户别偷看
    NN-<组件>/impl.py
```

备课的门禁(每个练习目录都要过,过了才给用户):

1. `uv run pytest NN-<组件>` 全红,而且红在 `NotImplementedError`——这就是"先失败"。
2. `LAB_IMPL=.answers/NN-<组件> uv run pytest NN-<组件>` 全绿——证明测试本身是对的、做得出来。
3. 每级测试只考这一级新加的那一个概念;测试名带级别(`test_L0_...`、`test_L1_...`),用户可以 `-k L1` 只跑一级。
4. 最后一级至少一条测试与 `oracle/` 对比(`allclose` / 逐字 / hash)。
5. 测试的报错信息要能教人:断言里写清期望什么、为什么(`assert out.shape == (T, d), "每个位置一个 d 维向量"`)。

## 四、每一级的练习循环

1. **出题**:用 README 里这一级的段落,说清只加的那一个概念、为什么需要它(上一级在哪儿不够,能跑就让用户跑一下看它坏)、接口(输入输出与 shape)、要守住的不变量。**不给实现,也不给伪代码。**
2. **先预测**:请用户先在纸上算极小例子,或写下"测试会输出什么"。预测错了不要紧,对比本身就是学习点。
3. **用户实现**:用户写 `impl.py`,运行 `uv run pytest NN-<组件> -k L<n>`。
4. **卡住时按阶梯给提示**,一次只上一级,每级之前先问"要提示吗":
   - 提示 1 · 方向:该想哪个概念、回看哪一级或原仓库哪一行(`path:line`);
   - 提示 2 · 关键观察:在小例子上给出一个中间值,让用户自己发现规律;
   - 提示 3 · 骨架:伪代码或缺了关键一行的代码;
   - 答案:只有用户明确说"看答案"才给,先问一句"要不要再试一次",给完在 PROGRESS.md 记"看了答案",并建议隔一天不看答案重写一遍。
5. **评审**(测试绿了之后):
   - 和原仓库对照:真实实现在哪里(`path:line`),它多做了什么(边界、性能、工程细节),为什么;
   - 指出一处可以更清楚或更快的地方,让用户自己改;
   - 不因为"能更好"就重写用户的代码。
6. **贯通题**:用户先答,Claude 再补。三选一:向上收(指着用户刚写的一行问它为什么存在)、改约束(规模 ×100 先改哪里)、预测(换一个输入会怎样)。用户答得好的说法,原话记进 PROGRESS.md 的"我自己的话"。

一级做完再出下一级,不要一次把所有题面倒给用户。

## 五、收尾

- 所有组件完成后,请用户**不看资料**画出架构总图(口述或草图都行):3–7 个零件、每条边传什么。Claude 对照 `00-scope.md` 的架构总图,只指出差异,不直接给正确答案。
- 从 `learning-lens.md` §四 的自测题里挑 3 道,用户先答。
- **融**:做一次嫁接实验——把自己实现里的一个零件换成另一种做法(或换进原仓库),先预测哪些测试会挂、输出偏多少,再运行(做法见学习循环第五节)。
- **收尾三问**(思想 / 直觉 / 方法,用户先答):各级练习里"先预测"错了的地方,汇总进 dot 库的 `predictions.md`;思想写成候选 dot;方法写进学习记录。
- 有 dot 库时写学习记录 `projects/course-<名字>.md`(见 SKILL.md "学习记录"),`类型` 写 `course`,并加一行 `- 模式:练习`;"核心心智模型"一栏优先用用户自己的话。

## 六、规则

- **不代写**:用户没说"看答案",就不给完整实现。用户的代码有 bug 时,指出哪个测试、哪个输入、哪一步的中间值不对,让用户自己改。
- **测试是裁判**:不为了让用户通过而改测试;测试确实写错了,公开说明错在哪里,改测试,并在 `.answers` 上重新验证。
- **进度可续**:每次开始先读 `lab/PROGRESS.md`,从上次停下的那一级接着练;每级结束更新它。
- **一次只问一件事**:出题、提示、追问都短,把思考留给用户。
