# scratch:dots — 从项目里提炼 dot，沉淀进个人知识库

> 路径说明:本 skill 目录是 `${CLAUDE_PLUGIN_ROOT}/skills/dots`（作为 scratch 插件安装时,该变量会被自动替换成绝对路径）；手动安装时就是本 SKILL.md 所在目录（加载时给出的 Base directory）。下文的 `scripts/`、`references/`、`templates/` 都相对这个目录。

## 目的

用户同时是 app 的使用者、设计者和开发者。他想积累的是"功底"，也就是乔布斯说的 connect the dots 里的 dot：不随框架、语言、年代变化的思想。

本 skill 的产出不是项目报告，而是 **dot 库的变化**。项目分析是一次性的，dot 库是复利的。

不要做"这个目录干嘛、那个模块干嘛"式的静态解剖。要回答三个问题：
1. 作者押注了什么（core bet）
2. 这个东西是怎么演化出来的（演化过程里的转折和放弃）
3. 哪些部分在代码生成越来越便宜的时代仍然值得人去学

**最重要的一条：功底只能长在用户自己身上。** Claude 负责找材料、找证据、做比对；"猜""判断""用自己的话说出来"这几步要尽量留给用户。

**dot 要能落地。** 一个 dot 只有在思想、心智模型、架构、实现四层之间打通才算真懂：说得出它押注什么，也指得到它在代码哪几行落地（四层的定义、设计决策卡、自测题见 `references/learning-lens.md`）。三面与四层的对应：体验面 ≈ 心智模型（用户能预测到什么），设计面 ≈ 架构与思想（为了 A 放弃了 B），实现面 ≈ 实现（必须写到 `path:line`）。

## 两种模式

| | 互动模式（默认） | 快速模式（用户说"快速"） |
|---|---|---|
| 检查点提问 | 有，共三个，见第三节 | 没有 |
| 先猜再看 | 由用户猜 | 跳过，项目笔记里写"未做" |
| 候选 dot | 先让用户说，再公布 Claude 的 | 直接给出 |
| 升级 dot | 提议后等用户确认 | 只提议，记为"待确认"，不移动文件 |

另有两种专门用法：**复盘模式**（盘点 dot 库，见第七节）和**对比模式**（两个解决同一问题的项目放在一起看，见第八节）。

互动模式整个过程最多问三个问题，不额外追问。用户回答"不知道"或"跳过"时，直接进入下一步，不要劝。

## 什么是 dot：四个测试

候选想法必须通过前三个，第四个用于排序：

1. **剥名测试**：去掉项目名、语言、框架名词，能否用一两句话讲清？
2. **复现测试**：是否在两个以上不相关的项目里以不同面目出现？首次出现的一律只算"候选"。
3. **拆除测试**：拿掉它，系统是塌了还是只是不方便？塌的才是核心。
4. **降价测试**：代码生成近乎免费后它还值钱吗？样板、胶水、语法细节在贬值；问题的切法、接口边界、验证机制、取舍判断在升值。

## 每个 dot 有两个互相独立的字段

- **复现状态**：`候选`（例证数 1）→ `已确认`（例证数 ≥2 且用户确认过）→ `归档`（长期未复现）
- **完整度**：`完整`（三面都有）或 `半个`（只有一两面）

两者不要混用：一个 dot 可以是"已确认但半个"，也可以是"候选但完整"。

### 三面

- **体验面**：用户感受到了什么
- **设计面**：在什么取舍下做的决定（为了 A 放弃了 B）
- **实现面**：代码里如何落地

**不要为了填满而编造。** 找不到就写"未找到"。

## 证据规则

- 每条关于"作者为什么这么做"的陈述，都必须标注来源：`[证据: commit abc123 / PR #45 / Issue #67 / 文件路径]`，否则标为 `[推断]`。
- **训练记忆不算证据。** 对有名的项目，Claude 可能"记得"作者的理由或采访内容，这类内容在仓库或网页里找到原文之前一律标 `[推断]`。
- 演化时间线里的"为什么"一栏，没有原文就写"无法确认"。

## 一、准备：定位 dot 库

1. dot 库位置按此顺序确定：用户本次明确指定的路径 → 环境变量 `DOT_LIBRARY` → 默认 `~/dot-library/`。
2. 首次使用且目录不存在时，先向用户确认路径，再创建以下结构，并执行 `git init`：

```
dot-library/
  index.md       # 索引：每个 dot 一行，比对时只读这个
  dots/          # 已确认的 dot
  candidates/    # 候选 dot
  archive/       # 归档的 dot
  projects/      # 每个分析过的项目一个笔记
  tensions.md    # dot 之间的张力记录
  changelog.md   # 每次分析后库里发生了什么变化
  graph.html     # /scratch:graph 生成的关系图，不入库（写进 .gitignore）
```

`projects/` 里还会出现 `scratch:blog` 写的 `blog-<slug>.md` 和 `scratch:repo` 写的 `course-<课程名>.md`（学习记录），它们不是 dot，但会出现在关系图上。

3. **先读 `index.md` 再分析**，不要逐个打开 dot 文件。只有在比对时怀疑同源，才打开对应的 dot 文件细读。
4. 如果 `index.md` 与目录里的实际文件不一致（用户手动改过），以文件为准，重建索引并告诉用户。

### 来自其他 skill 的材料

`scratch:blog` 产出的文章、`scratch:repo` 产出的课程，也可以作为例证来源，但要守两条：
- 例证仍然指向**原始出处**（博客原文链接、原仓库 `path:line`），不指向重写稿；重写稿里的比喻和补充不算证据。
- 博客例证的项目笔记文件名用 `blog-<slug>`，放在 `projects/`；它和讲同一个项目的仓库例证**不算两个独立例证**（复现测试要求不相关的来源）。

### 链接约定

全库统一使用 `[[文件名]]` 双链（与 Obsidian 兼容）。文件名在全库唯一，因此 dot 从 `candidates/` 移到 `dots/` 或 `archive/` 时链接不会断。
- dot 文件名：kebab-case 英文或拼音，例如 `append-only-log`
- 项目笔记文件名：`owner-repo`，例如 `tj-commander.js`
- `/scratch:graph` 靠链接所在的小节判断关系类型（`## 例证` → 例证，`## 连接` 里的 `- 同源异形：` 等 → 对应关系），所以链接要写在模板规定的位置

## 二、获取材料

### 2.1 克隆仓库
- 克隆到临时目录（如 `~/.cache/scratch/repos/<owner>-<repo>`），**不要放进 dot 库**。已存在则 `git pull`。
- 必须完整历史克隆，不能 `--depth 1`。若是浅克隆，执行 `git fetch --unshallow`。
- 网络受限无法克隆时，如实告诉用户，请用户提供本地副本，不要只凭 README 硬做。
- 大型仓库或 monorepo：先问用户关注哪个子目录。

### 2.2 历史考古
运行 `bash ${CLAUDE_PLUGIN_ROOT}/skills/dots/scripts/git-timeline.sh <仓库路径> [子目录]`。它已过滤 merge、bot、锁文件、依赖升级和格式化类提交，输出：基本信息、意图文件清单、首批 commit、提交密度、删除量最大的 commit、变更最频繁的文件、tag 时间线、贡献者。

### 2.3 意图文件（优先阅读）
脚本会列出 `CLAUDE.md`、`AGENTS.md`、`.cursorrules`、ADR、设计文档等。这些是作者写给协作者（包括 AI）的约束和决策，信息密度往往高于代码本身。README 里的 Non-goals、Why、Motivation 段落同属此类。

### 2.4 讨论记录（需要 `gh` 命令行）
克隆下来的仓库里没有 Issue 和 PR，要另外取：

```bash
gh pr list -R owner/repo --state closed --limit 50 --json number,title,mergedAt \
  --jq '.[] | select(.mergedAt == null) | "#\(.number) \(.title)"'      # 被拒绝的 PR
gh issue list -R owner/repo --state all --limit 30 --search "sort:comments-desc"  # 讨论最多的 Issue
gh issue list -R owner/repo --state closed --label wontfix --limit 30
gh pr view <编号> -R owner/repo --comments                               # 读具体讨论
```

`gh` 不可用或未登录时，告诉用户这部分没做，不要假装读过。

### 2.5 历史很短时转移重心
脚本提示"历史很短"，或首个 commit 就有几千行（常见于 AI 辅助开发或闭源后开源）时，考古信号弱。此时重心转向：
1. 意图文件
2. Issue / PR 讨论
3. **与前人对比**：这个问题之前有谁做过？作者的做法和它们差在哪？用 WebSearch 找作者的博客、发布帖、演讲来确认动机。这一步直接产出"传承"关系。

## 三、分析（含互动检查点）

### 3.1 检查点 A：先猜再看
在读 README 正文之前，只给用户看项目名和一句话简介，问：

> 如果你来做这个问题，会怎么切分？说一两句就行，说不出来也可以跳过。

把用户的原话记进项目笔记。分析结束时对比作者的切法，**差异处就是学习点**。

### 3.2 考古
重点读：
- **节奏变化点**：提交密度突然变化的时间段。变密可能是找到了对的抽象，也可能是换了维护者，要查证。
- **大删除**：被删掉的代码比留下的更有信息量。读 commit 说明和被删内容，回答"作者放弃了什么、为什么"。
- **最频繁变更的文件**：项目真正的"重力中心"，也可能是抽象没切对的地方。
- **被拒绝的 PR、wontfix 的 Issue、Non-goals**：作者品味的最佳窗口。

### 3.3 检查点 B：猜作者的赌注
把 3 到 5 个转折点和最关键的一两次"放弃"作为证据列给用户，但**先不说结论**，问：

> 看这几处转折和放弃，你觉得作者押注的是什么？

然后再给出 Claude 的判断：
- 一句话 core bet
- 类型："新的抽象"（换了一种切分问题的方式）或"新的组合"（老零件拼新东西）
- 最小内核：删掉 80% 之后，还能保留核心思想的那部分是什么

### 3.3.5 最小内核：从赌注追到代码
core bet 说完后，向下追到代码，不做全仓库的模块介绍：
- **阅读路线**：按阅读顺序列出 3 到 7 处 `path:line`，每处一句"去看什么、它在守护什么"。这就是"最小内核"在代码里的样子，也是给用户的动手入口。
- **关键设计决策**：从转折点和"放弃"里挑 1 到 2 个，各写一张设计决策卡（问题与约束 / 备选 / 选择与代价 / 证据 / 约束变了会怎样）。被拒绝的 PR、wontfix 的 Issue 往往就是现成的"备选"。
- 一个 dot 的实现面写不出 `path:line`，完整度就只能记"半个"。

### 3.4 提取候选 dot
每个项目 **1 到 3 个**，宁缺毋滥。每个候选走四个测试，标两个字段。通不过剥名测试的直接丢弃。

### 3.5 检查点 C：先说出来，再对答案
公布前先问：

> 这个项目里，你觉得有什么想法换个项目也能用？

再公布 Claude 的候选，并逐条对比：用户提到而 Claude 没有的，认真评估，通过测试就收入；Claude 有而用户没提到的，说清楚它为什么值得注意。

## 四、与 dot 库比对（核心步骤）

### 同源判断标准
说两个想法"同源"之前，必须同时写出：
1. **共同机制**：两者共享的那个具体机制（不能只是用词相似，比如都叫 log、都叫 cache 不算）
2. **区别**：它们在各自场景里有什么不同
3. **剥名后的那一句话**：对两边都成立

三条写不出来，就不算同源，作为新候选处理。**宁可漏连，不可错连。** 一旦错连，"例证数"这个指标就不可信了。

### 比对结果

| 情况 | 动作 |
|---|---|
| 与 `dots/` 中已有 dot 同源 | 追加例证，例证数 +1 |
| 与 `candidates/` 中候选同源 | 例证数变 2，**提议升级**：互动模式下把同源判断三条给用户看，用户确认后才移到 `dots/`；用户否认就作为新候选。快速模式下只在 changelog 记"待确认升级" |
| 库里没有 | 在 `candidates/` 新建，例证数 1 |

### 连接
为涉及的 dot 检查与库中其他 dot 的关系，只用四种：
- **同源异形**：表面不同，本质是同一个东西（标准同上）
- **张力**：两个 dot 互相拉扯（同时记入 `tensions.md`，说明拉扯点以及各自在什么场景下占上风）
- **依赖**：A 成立是因为 B 先存在
- **传承**：这个想法继承自更早的某个东西

没有真实关系就不写。

### `tensions.md` 条目

每条张力一个小节，标题里放两个链接（`/scratch:graph` 据此画红色虚线）：

```markdown
## [[append-only-log]] × [[compaction]]
- 拉扯点：可回溯 vs 存储空间
- [[append-only-log]] 占上风：需要审计、并发写
- [[compaction]] 占上风：历史很长、读多写少
```

### `changelog.md` 条目

```markdown
## YYYY-MM-DD [[owner-repo]]（第 N 个项目）
- 新增候选：...
- 强化：...（例证数 a → b）
- 升级：...
- 待确认升级：...
- 新发现的张力 / 连接：...
```

### 提交
写完后在 dot 库里执行 `git add -A && git commit -m "scratch:dots: <owner/repo>"`。dot 库自己的历史，就是用户功底的演化史。

## 六、给用户的最终回复

简短，重点是库的变化，不复述项目内容：

1. 一句话 core bet，以及和用户猜测的主要差异
2. **库的变化**：新增、强化、升级、待确认各列名字；新发现的张力或连接
3. 最值得花时间的 1 到 2 个点，以及一个动手练习；附最小内核阅读路线的第一站（`path:line`）
4. 材料覆盖情况里打 ✗ 的项（比如没读到 Issue），一句话说明
5. 需要用户动手的一件事：给升级的 dot 写"我自己的话"

## 七、复盘模式

用户说"盘点""复盘 dot 库"或类似意思时，不分析新项目。先运行 `uv run python ${CLAUDE_PLUGIN_ROOT}/skills/graph/scripts/learning_graph.py <dot库> --report`（它会顺带生成关系图 `graph.html`，把路径给用户），再读 `index.md`、`changelog.md`、`tensions.md`（必要时打开具体 dot 文件），报告：

- **功底所在**：例证数最多的几个 dot，其中"我自己的话"还空着的，提醒用户填写
- **建议归档**：首次记录后又分析了 10 个以上项目仍未复现的候选（用 changelog 里的项目序号计算）。用户同意后移到 `archive/`，不用惋惜
- **半个 dot**：已确认但完整度为"半个"的，指出缺哪一面，建议下次留意
- **悬空 dot**：实现面一直没有 `path:line` 的 dot，只停在思想层，建议下次分析时专门追到代码
- **孤立 dot** 和 `tensions.md` 中出现最多的张力
- **盲区**：例证全来自同一类项目（比如全是前端库、全是 CLI 工具）的 dot，可能是领域偏见而不是通用的不变性
- **悬挂链接与孤岛**：报告里列出的，问用户是拼错了还是一个值得记的想法；想和图一起逐项梳理时，转到 `/scratch:graph`
- **下一步**：推荐一类值得分析的项目，用来补盲区或验证某个候选

## 八、对比模式

用户给出两个解决**同一个问题**的项目（"对比 A 和 B""A 和 B 有什么不同""为什么有了 A 还要 B"），或在 `/scratch:learn` 里选了对比时使用。同一个问题的两种做法放在一起，最容易看出取舍：哪些是问题本身逼出来的（不变量），哪些是作者的选择（张力）。

### 8.1 先确认能比
- **是同一个问题吗**：两边各用一句剥名的话说出它在解决什么。说不成同一句，就告诉用户它们不在比同一件事，建议分别分析。
- **是独立的吗**：查 fork 关系、README 里的致谢、作者是否相同、是否"X 的 Rust 移植"。一个派生自另一个时，它们之间是**传承**关系，不算两个独立例证。
- 两个仓库按第二节各自准备材料（克隆、`git-timeline.sh`、意图文件、讨论记录）。

### 8.2 互动检查点（快速模式跳过）
- **检查点 A**：只给两个项目名和一句话简介，问用户："你觉得它俩最大的不同会在哪？"
- **检查点 B**：列出两边在同一处的不同选择（只列事实和证据），问用户："各自是为了什么？"再给出 Claude 的判断。
- **检查点 C**：问用户："抛开不同，两边都没法绕开的是什么？"再公布 Claude 的候选不变量。

### 8.3 分析
并排写，每一行都要有两边的证据（`path:line` / commit / PR / 文档）：

| 维度 | A | B |
|---|---|---|
| 核心赌注（为了什么放弃了什么） | | |
| 最小内核（阅读路线第一站） | | |
| 关键数据结构 | | |
| 同一个约束下的不同选择（设计决策卡并排） | | |
| 演化：有没有一方后来改成了另一方的做法 | | |

"后来改成了对方的做法"是最强的证据，说明那个选择被现实检验过；找到就重点写。

### 8.4 写入 dot 库
- **两边都有的机制**（通过四个测试）：按第四节比对。库里没有的，新建候选，例证直接写两条；仍然只是候选，升级要走"提议 → 用户确认"。
- **两边不同的选择**：写进 `tensions.md`，按张力格式写清各自在什么场景占上风，并附两边证据。
- 两个项目各写一份项目笔记，另写一份对比笔记 `projects/compare-<a>-vs-<b>.md`：`## 对比的项目` 下链接两份项目笔记，`## 并排` 放上面的表，`## 共同的 dot` 和 `## 新的张力` 下链接涉及的 dot（不要用"例证""本项目涉及的 dot"做标题：对比笔记不是例证来源，关系图会把它画成普通关联）。
- `changelog.md` 记一条，标题写 `[[compare-<a>-vs-<b>]]`。

### 8.5 给用户的回复
1. 一句话：它们的根本差别是什么（用户在检查点 A 的猜测对在哪、偏在哪）；
2. 共同的不变量与新增的张力；
3. 一个动手练习：例如"用 B 的做法改写 A 的某个小功能，看哪里别扭"——别扭的地方就是取舍所在。

## 原则

- **思考留给用户**：能让用户先说的，Claude 后说。
- **诚实优先于完整**：没有证据就标推断或写找不到，宁可 dot 少也不要编。
- **宁可漏连，不可错连**：同源判断三条写不出来就不连。
- **新 dot 先进候选区**：复现才是最诚实的指标，升级要用户确认。
- **不代写"我自己的话"**。
- **不输出项目的模块功能介绍**，除非它直接是某个 dot 的证据。
- **dot 要能落地**：思想追不到代码的，标"半个"，不硬凑。
