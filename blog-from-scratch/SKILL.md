# blog-from-scratch

输入一篇博客(链接或正文),输出一页排版好的 HTML:**读者读完能"自己想出来"的重写**——还原问题 → 还原推理(连同原文的图) → 提炼心智模型 → 给出检验。

好的博客读完像"哦原来如此";读者两天后却说不出为什么。这个 skill 补的就是这一步:把作者脑中那条"为什么会这么想"的路,摊开成读者能走的台阶。

> 路径说明:`scripts/`、`templates/`、`references/` 相对本 SKILL.md 所在目录;调用脚本时用绝对路径,例如 `uv run --with markdown python ~/.claude/skills/blog-from-scratch/scripts/build_html.py`。

## 它不是什么

- 不是摘要:摘要给结论,这里给**得出结论的路**。
- 不是翻译或改写:不逐段跟着原文走,按"理解的顺序"重排,而不是"作者写的顺序"。
- 不是评论:先忠实还原作者,再(可选、单独标注)提自己的看法。

## 输入:先把原文拿全,包括图

用户给**链接**或**正文**(或两者)即可,不要要求更多。

- **正文**:用 `curl` 下载原始 HTML 再转纯文本(WebFetch 会让小模型先摘要,长文会丢细节)。内容很短、只有导航、被付费墙挡住或明显截断时,**停下告诉用户**,请他粘贴正文,不要凭标题和记忆编造。
- **图**:从 HTML 里找出所有 `<img>`,逐张下载到工作目录的 `images/`,**然后逐张打开看**。博客里的图往往是作者最精心设计的讲解——手算例子、数据流、对比——文字只是图的旁白,丢了图就丢了一半内容。
- 看不了图(当前模型没有视觉能力)或下载失败的图,才退回"按图注和上下文推断",并在文中和"边界"里明说是哪几张。不能因为麻烦就整体跳过。
- 用户没说的偏好(深度、篇幅、读者背景)不要追问,用默认:读者聪明但不是该领域专家;语言跟随用户提问所用的语言(中文提问就中文写,术语首次出现附英文原词)。

## 工作流

| # | 步骤 | 做什么 | 产物 |
|---|---|---|---|
| 1 | 取文 | 拿到完整正文 + 全部图;记下标题、作者、日期、链接 | 原文与图在手 |
| 2 | 图清单 | 逐张看图,按 `references/figures.md` 建清单:这张图画了什么、教了什么、怎么处理(沿用原图 / 重画 SVG / 改成表格或代码块 / 合并 / 舍弃并写明理由) | `figures-list` 工作笔记 |
| 3 | 解剖 | 按 `references/dissection.md` 提取:作者在回答什么问题、论证骨架、关键例子、隐含假设、被反驳的"直觉做法" | `notes` 工作笔记(写到暂存目录,不进最终稿) |
| 4 | 提炼心智模型 | 找出 1–4 个读者带走的"思维方式"(不是知识点),每个能一句话说清、能用在别处 | 心智模型清单 |
| 5 | 设计台阶 | 决定重建顺序:从读者已有的世界出发,每一步只引入一个新东西(`references/rebuild.md`);图清单里的图按需要挂到台阶上 | 台阶大纲 |
| 6 | 起草 | 按 `templates/article.md` 写成 Markdown,图写成独立的 `figures/*.svg` 并用图语法引用 | `<slug>.md` + `figures/` |
| 7 | 核验 | 对照原文逐条检查忠实度;有代码/数字/公式就**真的跑/算一遍**;**图里的每个数字和标签对照原图复核**;能数的事实(图数、步数)真数一遍 | 核验通过 |
| 8 | 出页 | `uv run --with markdown python scripts/build_html.py <slug>.md --embed-images`,再用 Chrome 无头截图检查(见下) | `<slug>.html` |
| 9 | 读者自测 | 自问:没读过原文的人能否复述核心论证、能否回答文末检验题?每一段能否脱离上下文读通? | 修订 |

步骤 2、3、4 是质量的来源,别跳过直接开写——直接写出来的东西往往只是原文的缩写。

## 写作原则(以及为什么)

1. **先问题,后答案。** 读者不知道问题为什么难,就不会觉得答案妙。先让他体会"天真做法为什么行不通",最好用一个小到能手算的例子。
2. **优先用作者自己的例子。** 作者的手算例子(图里的数字、代码里的 prompt)是最好的素材:读者之后回到原文能对上号。自己另造例子只在原文没有、或原例子太复杂时。
3. **先画面,后术语。** 术语是标签,标签要贴在已经理解的东西上。先用日常场景或最小例子建立直觉,再给名字。
4. **每一步只加一个新概念。** 两个新东西同时出现,读者就分不清哪个在起作用。
5. **讲"为什么这样想",不只是"是什么"。** 作者面对岔路时选了哪边、放弃了什么、为什么——这才是可迁移的思维模式。
6. **心智模型要能迁移。** 每个模型配一个"换个领域也成立"的例子或一句"遇到什么情况时想起它"。只能用于本文的,是知识点,不是心智模型。
7. **区分三种声音。** 作者的观点 / 作者引用的事实 / 我的补充。凡是原文没有、我加的解释、比喻、例子、实验,都放进 `[!supp]` 补充块,不让读者误以为是作者说的。
8. **每句话要能读通。** 比喻只在能说清"哪里像、哪里不像"时才用;文学化的修辞、凑出来的金句、读起来拗口的句子,宁可删掉。写完通读一遍,读不通的句子就是没想清楚的地方。
9. **诚实标出边界。** 原文没论证只是断言的地方、我没核实的地方、适用范围的限制,集中写在文末一个"边界"小节,正文保持干净。
10. **能算就算,能跑就跑。** 原文里的数字、代码、推导,自己验证一遍;输出要来自真实运行,不是想象。验证不过要如实写出来,别悄悄改成对的。
11. **版权与忠实。** 用自己的话重述;原图表意清楚就**直接沿用并标明出处**(不裁剪、不改动,图注写自己的结论并附原图链接),需要重画时用自己的方式画、不描摹;引用原文文字只用短句;文首写明来源链接与作者。

## 输出

默认产出两样东西,放在当前目录(用户指定了位置就用指定的),文件名用文章主题的 slug:

- `<slug>.html`:读者看的成品,单文件、自带排版(目录、提示块、明暗主题、手机可读),图已内联(原图沿用的会内嵌进文件,断网也能看)。
- `<slug>.md` 和 `figures/*.svg`:源文件,留着方便改。

Markdown 的写法见 `templates/article.md`;图怎么选、怎么画见 `references/figures.md`。

**出页后必须看一眼效果**:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu \
  --screenshot=/tmp/check.png --window-size=1300,4000 file://$PWD/<slug>.html
```

然后打开截图,检查图有没有文字溢出框外、箭头是否指对、提示块是否各自成块。没有 Chrome 就在 SVG 里留足边距并保守估计文字宽度(中文每字约 14px 宽)。

写完在对话里只给:文件路径、一两句话说这篇的核心心智模型、以及核验中发现的任何问题——不要把整篇文章再贴一遍。

篇幅跟随原文的信息量,不是原文长度:一篇 800 字的观点文可能只需要一个模型、一页纸;一篇 8000 字的技术长文可能需要多个台阶。宁可短而清楚。

## 不要做

- 按原文段落顺序逐段复述。
- 堆砌"总结/要点/Takeaways"项目符号来代替推理。
- 用原文没有的"升华"收尾(如泛泛的人生道理)。
- 在没拿到正文时假装读过;在能看图时不看图。
- **静默丢图**:每张原图要么沿用、要么重画/转写,要么在图清单和"边界"里写明为什么不要。
- 为了"原创"而重画本来就很清楚的原图——清楚就直接用。
- 为显得全面而覆盖原文的每个细枝末节——次要内容一句话带过或舍弃。

## 文件地图

- `references/dissection.md` — 解剖博客的问题清单与不同体裁(技术/观点/叙事)的侧重
- `references/rebuild.md` — 怎么设计重建台阶、造直觉的几种手法、心智模型的检验标准
- `references/figures.md` — 图清单怎么建、沿用还是重画的判断、手写 SVG 的规范与样板
- `templates/article.md` — 输出文章的 Markdown 结构与可用语法
- `templates/style.css` — HTML 样式(由脚本内嵌,通常不用改)
- `scripts/build_html.py` — Markdown → 单文件 HTML(内联 SVG、内嵌原图、提示块、目录)
