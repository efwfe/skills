# connect-dots：从项目里提炼 dot，沉淀进个人知识库

## 目的

用户同时是 app 的使用者、设计者和开发者。他想积累的是"功底"，也就是乔布斯说的 connect the dots 里的 dot：不随框架、语言、年代变化的思想。

本 skill 的产出不是项目报告，而是 **dot 库的变化**。项目分析是一次性的，dot 库是复利的。

不要做"这个目录干嘛、那个模块干嘛"式的静态解剖。要回答三个问题：
1. 作者押注了什么（core bet）
2. 这个东西是怎么演化出来的（演化过程里的转折和放弃）
3. 哪些部分在代码生成越来越便宜的时代仍然值得人去学

**最重要的一条：功底只能长在用户自己身上。** Claude 负责找材料、找证据、做比对；"猜""判断""用自己的话说出来"这几步要尽量留给用户。

## 两种模式

| | 互动模式（默认） | 快速模式（用户说"快速"） |
|---|---|---|
| 检查点提问 | 有，共三个，见第三节 | 没有 |
| 先猜再看 | 由用户猜 | 跳过，项目笔记里写"未做" |
| 候选 dot | 先让用户说，再公布 Claude 的 | 直接给出 |
| 升级 dot | 提议后等用户确认 | 只提议，记为"待确认"，不移动文件 |

互动模式整个过程最多问三个问题，不额外追问。用户回答"不知道"或"跳过"时，直接进入下一步，不要劝。

## 什么是 dot：四个测试

候选想法必须通过前三个，第四个用于排序：

1. **剥名测试**：去掉项目名、语言、框架名词，能否用一两句话讲清？
2. **复现测试**：是否在两个以上不相关的项目里以不同面目出现？首次出现的一律只算"候选"。
3. **拆除测试**：拿掉它，系统是塌了还是只是不方便？塌的才是核心。
4. **降价测试**：代码生成近乎免费后它还值钱吗？样板、胶水、语法细节在贬值；问题的切法、接口边界、验证机制、取舍判断在升值。

## 每个 dot 有两个互相独立的字段

- **复现状态**：`候选`（例证数 1）→ `已确认`（例证数 ≥2 且用户确认过）→ `归档`（长期未复现）
- **完整度**：`完整`（三面都有）或 `半个`（只有一两面）

两者不要混用：一个 dot 可以是"已确认但半个"，也可以是"候选但完整"。

### 三面

- **体验面**：用户感受到了什么
- **设计面**：在什么取舍下做的决定（为了 A 放弃了 B）
- **实现面**：代码里如何落地

**不要为了填满而编造。** 找不到就写"未找到"。

## 证据规则

- 每条关于"作者为什么这么做"的陈述，都必须标注来源：`[证据: commit abc123 / PR #45 / Issue #67 / 文件路径]`，否则标为 `[推断]`。
- **训练记忆不算证据。** 对有名的项目，Claude 可能"记得"作者的理由或采访内容，这类内容在仓库或网页里找到原文之前一律标 `[推断]`。
- 演化时间线里的"为什么"一栏，没有原文就写"无法确认"。

## 一、准备：定位 dot 库

1. dot 库位置按此顺序确定：用户本次明确指定的路径 → 环境变量 `DOT_LIBRARY` → 默认 `~/dot-library/`。
2. 首次使用且目录不存在时，先向用户确认路径，再创建以下结构，并执行 `git init`：

```
dot-library/
  index.md       # 索引：每个 dot 一行，比对时只读这个
  dots/          # 已确认的 dot
  candidates/    # 候选 dot
  archive/       # 归档的 dot
  projects/      # 每个分析过的项目一个笔记
  tensions.md    # dot 之间的张力记录
  changelog.md   # 每次分析后库里发生了什么变化
```

3. **先读 `index.md` 再分析**，不要逐个打开 dot 文件。只有在比对时怀疑同源，才打开对应的 dot 文件细读。
4. 如果 `index.md` 与目录里的实际文件不一致（用户手动改过），以文件为准，重建索引并告诉用户。

### 链接约定

全库统一使用 `[[文件名]]` 双链（与 Obsidian 兼容）。文件名在全库唯一，因此 dot 从 `candidates/` 移到 `dots/` 或 `archive/` 时链接不会断。
- dot 文件名：kebab-case 英文或拼音，例如 `append-only-log`
- 项目笔记文件名：`owner-repo`，例如 `tj-commander.js`

## 二、获取材料

### 2.1 克隆仓库
- 克隆到临时目录（如 `~/.cache/connect-dots/<owner>-<repo>`），**不要放进 dot 库**。已存在则 `git pull`。
- 必须完整历史克隆，不能 `--depth 1`。若是浅克隆，执行 `git fetch --unshallow`。
- 网络受限无法克隆时，如实告诉用户，请用户提供本地副本，不要只凭 README 硬做。
- 大型仓库或 monorepo：先问用户关注哪个子目录。

### 2.2 历史考古
运行本 skill 目录下的 `scripts/git-timeline.sh <仓库路径> [子目录]`。它已过滤 merge、bot、锁文件、依赖升级和格式化类提交，输出：基本信息、意图文件清单、首批 commit、提交密度、删除量最大的 commit、变更最频繁的文件、tag 时间线、贡献者。

### 2.3 意图文件（优先阅读）
脚本会列出 `CLAUDE.md`、`AGENTS.md`、`.cursorrules`、ADR、设计文档等。这些是作者写给协作者（包括 AI）的约束和决策，信息密度往往高于代码本身。README 里的 Non-goals、Why、Motivation 段落同属此类。

### 2.4 讨论记录（需要 `gh` 命令行）
克隆下来的仓库里没有 Issue 和 PR，要另外取：

```bash
gh pr list -R owner/repo --state closed --limit 50 --json number,title,mergedAt \
  --jq '.[] | select(.mergedAt == null) | "#\(.number) \(.title)"'      # 被拒绝的 PR
gh issue list -R owner/repo --state all --limit 30 --search "sort:comments-desc"  # 讨论最多的 Issue
gh issue list -R owner/repo --state closed --label wontfix --limit 30
gh pr view <编号> -R owner/repo --comments                               # 读具体讨论
```

`gh` 不可用或未登录时，告诉用户这部分没做，不要假装读过。

### 2.5 历史很短时转移重心
脚本提示"历史很短"，或首个 commit 就有几千行（常见于 AI 辅助开发或闭源后开源）时，考古信号弱。此时重心转向：
1. 意图文件
2. Issue / PR 讨论
3. **与前人对比**：这个问题之前有谁做过？作者的做法和它们差在哪？用 WebSearch 找作者的博客、发布帖、演讲来确认动机。这一步直接产出"传承"关系。

## 三、分析（含互动检查点）

### 3.1 检查点 A：先猜再看
在读 README 正文之前，只给用户看项目名和一句话简介，问：

> 如果你来做这个问题，会怎么切分？说一两句就行，说不出来也可以跳过。

把用户的原话记进项目笔记。分析结束时对比作者的切法，**差异处就是学习点**。

### 3.2 考古
重点读：
- **节奏变化点**：提交密度突然变化的时间段。变密可能是找到了对的抽象，也可能是换了维护者，要查证。
- **大删除**：被删掉的代码比留下的更有信息量。读 commit 说明和被删内容，回答"作者放弃了什么、为什么"。
- **最频繁变更的文件**：项目真正的"重力中心"，也可能是抽象没切对的地方。
- **被拒绝的 PR、wontfix 的 Issue、Non-goals**：作者品味的最佳窗口。

### 3.3 检查点 B：猜作者的赌注
把 3 到 5 个转折点和最关键的一两次"放弃"作为证据列给用户，但**先不说结论**，问：

> 看这几处转折和放弃，你觉得作者押注的是什么？

然后再给出 Claude 的判断：
- 一句话 core bet
- 类型："新的抽象"（换了一种切分问题的方式）或"新的组合"（老零件拼新东西）
- 最小内核：删掉 80% 之后，还能保留核心思想的那部分是什么

### 3.4 提取候选 dot
每个项目 **1 到 3 个**，宁缺毋滥。每个候选走四个测试，标两个字段。通不过剥名测试的直接丢弃。

### 3.5 检查点 C：先说出来，再对答案
公布前先问：

> 这个项目里，你觉得有什么想法换个项目也能用？

再公布 Claude 的候选，并逐条对比：用户提到而 Claude 没有的，认真评估，通过测试就收入；Claude 有而用户没提到的，说清楚它为什么值得注意。

## 四、与 dot 库比对（核心步骤）

### 同源判断标准
说两个想法"同源"之前，必须同时写出：
1. **共同机制**：两者共享的那个具体机制（不能只是用词相似，比如都叫 log、都叫 cache 不算）
2. **区别**：它们在各自场景里有什么不同
3. **剥名后的那一句话**：对两边都成立

三条写不出来，就不算同源，作为新候选处理。**宁可漏连，不可错连。** 一旦错连，"例证数"这个指标就不可信了。

### 比对结果

| 情况 | 动作 |
|---|---|
| 与 `dots/` 中已有 dot 同源 | 追加例证，例证数 +1 |
| 与 `candidates/` 中候选同源 | 例证数变 2，**提议升级**：互动模式下把同源判断三条给用户看，用户确认后才移到 `dots/`；用户否认就作为新候选。快速模式下只在 changelog 记"待确认升级" |
| 库里没有 | 在 `candidates/` 新建，例证数 1 |

### 连接
为涉及的 dot 检查与库中其他 dot 的关系，只用四种：
- **同源异形**：表面不同，本质是同一个东西（标准同上）
- **张力**：两个 dot 互相拉扯（同时记入 `tensions.md`，说明拉扯点以及各自在什么场景下占上风）
- **依赖**：A 成立是因为 B 先存在
- **传承**：这个想法继承自更早的某个东西

没有真实关系就不写。

## 五、写入文件

覆盖已有文件前先读取，只追加或局部修改，不整体重写用户编辑过的内容（特别是"我自己的话"一栏）。

### `index.md`

```markdown
# dot 索引

| dot | 一句话 | 状态 | 完整度 | 例证数 |
|---|---|---|---|---|
| [[append-only-log]] | 只追加不修改，用历史换取可回溯和并发安全 | 已确认 | 完整 | 3 |
```

### dot 文件模板

```markdown
# <dot 名称>

> 一句话（剥名后的表述，不含任何项目名或技术栈名词）：

- 状态：候选 | 已确认 | 归档
- 完整度：完整 | 半个
- 例证数：N
- 首次记录：YYYY-MM-DD
- 最后更新：YYYY-MM-DD

## 三面
- **体验面**：
- **设计面**（为了 A 放弃了 B）：
- **实现面**：

## 例证
1. [[owner-repo]]：它在这里以什么面目出现。[证据: ...]
2. [[owner-repo]]：面目；与例证 1 的区别：...

## 降价测试
升值还是贬值，为什么：

## 连接
- 同源异形：[[...]]
- 张力：[[...]]（见 [[tensions]]）
- 依赖：[[...]]
- 传承：[[...]] 或外部来源

## 我自己的话
（留空。由用户在确认升级时填写，Claude 不代写。）
```

### 项目笔记模板（`projects/<owner-repo>.md`）

```markdown
# <owner/repo>

- 链接：
- 分析日期：
- 分析范围：<首个 commit> .. <HEAD commit>（子目录：...）
- 模式：互动 | 快速
- 材料覆盖：git 历史 ✓/✗ · 意图文件 ✓/✗ · Issue/PR ✓/✗ · 前人对比 ✓/✗

## 先猜再看
- 我的猜测（原话）：
- 作者实际怎么切：
- 差异（学习点）：

## 核心赌注
- 我的判断（检查点 B 原话）：
- 一句话：
- 类型：新的抽象 | 新的组合
- 最小内核：

## 演化时间线（3 到 5 个转折点）
| 时间 | commit / PR | 发生了什么 | 为什么（[证据] / [推断] / 无法确认） |
|---|---|---|---|

## 被放弃的东西
- ... [证据: ...]

## 本项目涉及的 dot
- [[dot]]（新增候选 / 强化 / 升级 / 待确认升级）
- 我在检查点 C 说出的：

## 值得深学 / 可以跳过
- 值得深学（按"可迁移性 × 抗贬值度"排序）：
- 可以跳过（样板、胶水、项目特有细节）：

## 动手练习
一个具体的小练习，例如"不看源码，先自己设计 XX 这一层，再对比作者"。
```

### `changelog.md` 条目

```markdown
## YYYY-MM-DD [[owner-repo]]（第 N 个项目）
- 新增候选：...
- 强化：...（例证数 a → b）
- 升级：...
- 待确认升级：...
- 新发现的张力 / 连接：...
```

### 提交
写完后在 dot 库里执行 `git add -A && git commit -m "connect-dots: <owner/repo>"`。dot 库自己的历史，就是用户功底的演化史。

## 六、给用户的最终回复

简短，重点是库的变化，不复述项目内容：

1. 一句话 core bet，以及和用户猜测的主要差异
2. **库的变化**：新增、强化、升级、待确认各列名字；新发现的张力或连接
3. 最值得花时间的 1 到 2 个点，以及一个动手练习
4. 材料覆盖情况里打 ✗ 的项（比如没读到 Issue），一句话说明
5. 需要用户动手的一件事：给升级的 dot 写"我自己的话"

## 七、复盘模式

用户说"盘点""复盘 dot 库"或类似意思时，不分析新项目，而是读 `index.md`、`changelog.md`、`tensions.md`（必要时打开具体 dot 文件），报告：

- **功底所在**：例证数最多的几个 dot，其中"我自己的话"还空着的，提醒用户填写
- **建议归档**：首次记录后又分析了 10 个以上项目仍未复现的候选（用 changelog 里的项目序号计算）。用户同意后移到 `archive/`，不用惋惜
- **半个 dot**：已确认但完整度为"半个"的，指出缺哪一面，建议下次留意
- **孤立 dot** 和 `tensions.md` 中出现最多的张力
- **盲区**：例证全来自同一类项目（比如全是前端库、全是 CLI 工具）的 dot，可能是领域偏见而不是通用的不变性
- **下一步**：推荐一类值得分析的项目，用来补盲区或验证某个候选

## 原则

- **思考留给用户**：能让用户先说的，Claude 后说。
- **诚实优先于完整**：没有证据就标推断或写找不到，宁可 dot 少也不要编。
- **宁可漏连，不可错连**：同源判断三条写不出来就不连。
- **新 dot 先进候选区**：复现才是最诚实的指标，升级要用户确认。
- **不代写"我自己的话"**。
- **不输出项目的模块功能介绍**，除非它直接是某个 dot 的证据。
